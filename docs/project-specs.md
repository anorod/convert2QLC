# Final Technical Requirements: Picolo to QLC+ Converter

**Version:** 3.0
**Date:** May 24, 2024

## 1. Project Summary

The objective is to develop an application that automates the conversion of lighting show files, generated by the "Print" function of a **Picolo** control console, to the file format (`.qxc`) compatible with the **QLC+** software.

The application will consist of two main, decoupled components: a **Backend** (conversion engine) that performs the transformation logic and a **Frontend** (web interface) that allows users to interact with the service.

## 2. System Architecture

A containerized microservices architecture will be implemented, decoupling the user interface from the business logic to ensure modularity, scalability, and reusability of the conversion engine.

*   **Backend Container:** An independent service that exposes a RESTful API. Its sole responsibility is to receive a Picolo text file and return a QLC+ XML file.
*   **Frontend Container:** A web application (e.g., PHP/Node.js) that serves the user interface and communicates with the Backend API.
*   **Orchestration:** **Docker Compose** will be used to define, build, and run both containers, managing the internal network for their communication.

### Architecture Diagram
```
[User] <--> [Browser] <--> [Frontend Container (PHP/Apache)]
                                       |
                                       V (API Call to http://backend:PORT)
                                       |
                             [Backend Container (Python/etc.)]
```

## 3. Detailed Conversion Flow

The conversion process will be performed in a single pass on the backend, following these logical steps:

### Step 1: Pre-analysis of the Picolo File

1.  The backend receives the `.txt` file from Picolo.
2.  It performs a full read of the file to extract and store in memory:
    *   **Cue List Data:** An ordered list of objects, each containing `CueNum`, `TI` (Time In), `TO` (Time Out), `TW` (Time Wait), and `Text`.
    *   **Channel Data per Cue:** A dictionary or map where the key is the `CueNum` and the value is another map of `ChannelNum` to `Level`.
    *   **Maximum Channel:** During channel parsing, the highest channel number used throughout the show (`max_channel_number`) must be identified and saved.

### Step 2: Generation of Base XML and Scenes

1.  **Create XML Structure:** The backend starts building a new XML document with the base structure of a QLC+ `.qxc` file.
2.  **Create Generic Fixture:** A single `<Fixture>` node is added to the XML:
    *   **Manufacturer:** `Generic`
    *   **Model:** `Generic`
    *   **Mode:** `"[max_channel_number] Channel"` (The value is taken from the pre-analysis).
    *   **ID:** `0`
    *   **Name:** `Picolo Dimmers`
    *   **Universe:** `0`
    *   **Address:** `0`
    *   **Channels:** `max_channel_number`
3.  **Generate Scenes:** Iterate over the stored channel data per cue. For each cue:
    *   A `<Function Type="Scene">` node is created with a sequential `ID` (starting at `0`) and a `Name` formed by `"[CueNum] [CueText]"`.
    *   A child node `<FixtureVal ID="0">` is created.
    *   The value string is constructed by applying the **level conversion logic** (see section 4.2.1).
    *   A mapping is saved between the Picolo `CueNum` (e.g., "2.5") and the generated scene `ID` (e.g., "2").

### Step 3: Generation of the Chaser (Cue List)

1.  A single `<Function Type="Chaser">` node is created with the next available `ID` and a name (e.g., "Converted Show").
2.  Iterate over the ordered Cue List stored in memory.
3.  For each cue in the list, a `<Step>` node is added to the Chaser:
    *   **Step Content:** The corresponding scene `ID` (obtained from the mapping saved in the previous step).
    *   **Time Attributes:** The `FadeIn`, `FadeOut`, and `Hold` attributes are calculated by applying the **time mapping logic** (see section 4.2.2).
    *   **`Note` Attribute:** The `Text` of the cue is assigned.

## 4. Backend Requirements

### 4.1. Core Functionality
*   **Parse Picolo File:** Analyze the plain text format to extract the Cue List and channel levels for each cue.
*   **Input File Validation:** Ensure the uploaded file is of type `text/plain` and has a `.txt` extension. Additionally, the file size must be less than a configurable limit (e.g., 5MB) to prevent performance issues or abuse.
*   **Generate QLC+ File:** Construct a valid XML file (`.qxc`) following the detailed structure and logic.

### 4.2. Transformation Logic (Business Rules)

#### 4.2.1. Channel Level Conversion
*   **Input Format (Picolo):** String.
    *   Numeric `"0"` to `"99"` (percentage).
    *   Special `"FF"` (100%).
*   **Output Format (QLC+):** Decimal integer (0-255).
*   **Conversion Formula (Pseudocode):**
    ```
    if picolo_value == "FF":
        qlc_value = 255
    else:
        percentage = int(picolo_value)
        qlc_value = round((percentage / 100.0) * 255)
    ```
*   **Channel Mapping:** QLC+ channels are 0-based.
    *   `QLC_Channel_Index = Picolo_Channel_Number - 1`

#### 4.2.2. Time Mapping
Units in Picolo are **seconds**, and in QLC+ they are **milliseconds**.
*   **Fade In:** `FadeIn_ms = float(TI_Picolo) * 1000`.
*   **Fade Out:** Crossfade logic is applied. The `FadeOut` of step `N` is the `FadeIn` of step `N+1`.
    *   `FadeOut_ms(Step_N) = float(TI_Picolo_of_Next_Cue) * 1000`.
    *   For the last step, its own `TO` value will be used: `float(TO_Picolo_Last) * 1000`.
*   **Hold:**
    *   If `TW` is `"Manua"` -> `Hold_ms = 4294967294`.
    *   If `TW` is numeric (e.g., `"5"`) -> `Hold_ms = float(TW) * 1000`.
    *   If `TW` is alphanumeric (e.g., `"Manua4"`) -> `Hold_ms = int(numeric_part) * 1000`.

### 4.3. Backend API
*   **Endpoint:** `POST /api/v1/convert`
*   **Request Body:** `multipart/form-data` with a `file` field containing the Picolo `.txt`.
*   **Success Response:**
    *   **Code:** `200 OK`
    *   **Headers:** `Content-Type: application/json`
    *   **Body:** A JSON object with the conversion data.
        ```json
        {
          "summary": {
            "cueCount": 0,
            "channelCount": 0,
            "scenes": [
              { "id": 0, "name": "" }
            ]
          },
          "fileName": "show.qxc",
          "fileContent": "<?xml version=\"1.0\" encoding=\"UTF-8\"?>..."
        }
        ```
*   **Error Response:** `400 Bad Request` or `500 Internal Server Error` with a JSON body (`{"error": "descriptive message"}`).

### 4.4. Recommended Tech Stack
*   **Language:** **Python**. It is an ideal language for text parsing and data manipulation, which is the core of the conversion logic.
*   **API Framework:** **FastAPI**.
    *   **Performance:** It is extremely fast, comparable to Node.js.
    *   **Ease of Use:** Reduces the amount of code needed to create a robust API.
    *   **Automatic Documentation:** Automatically generates interactive API documentation (with Swagger UI), which is fantastic for testing the endpoint during development.
    *   **Data Validation:** Uses Python typing to automatically validate requests, making the API more secure.

## 5. Frontend Requirements

### 5.1. User Interface and Flow
1.  The user sees a page with a form to upload a file and a "Convert" button.
2.  After selecting the file and clicking, a loading animation is displayed.
3.  **Client-side validation** of the file (type, size).
4.  The application sends the file to the backend API via the Frontend server.
5.  **On success:**
    *   The loading animation disappears.
    *   A summary of the conversion is displayed on the screen: "Conversion successful: **X** cues and **Y** channels detected."
    *   Optionally, a table with the list of generated scenes can be displayed.
    *   A "Download .qxc File" button appears. When clicked, the frontend generates and downloads the file using the data received from the API.
6.  **On error:** A clear and understandable error message is displayed.

### 5.2. Technologies

The frontend will be developed with an interactive stack for an enhanced user experience.

*   **Framework:** **Vue.js** or **React**.
*   **Description:** To implement dynamic features like previewing results without reloading the page, a modern JavaScript framework will be used. This allows for the creation of a Single Page Application (SPA) that offers a much smoother and faster user experience.
*   **Server:** The frontend will be a set of static files (HTML, CSS, JS) that can be served by a lightweight web server like **Nginx**.

## 6. Deployment Requirements (Docker)

The project will be deployed using Docker and Docker Compose.

### 6.1. Recommended Directory Structure
```
/project-converter/
├── docker-compose.yml
├── backend/
│   ├── Dockerfile
│   └── src/
└── frontend/
    ├── Dockerfile
    └── src/
```

### 6.2. Backend Container
*   **`Dockerfile`:** Will define a lightweight image (e.g., `python:3.10-slim`) that installs dependencies, copies the code, and runs an API server (e.g., Gunicorn).
*   **Network:** Will be accessible within the Docker network by its service name (e.g., `backend`).

### 6.3. Frontend Container
*   **`Dockerfile`:** Will define a web server image with PHP/Node.js (e.g., `php:8.1-apache` or `node:18-alpine`), copying the source code and ensuring necessary extensions are installed.
*   **Network:** Will communicate with the backend via its service name (e.g., `http://backend:5000/api/v1/convert`).

### 6.4. Orchestration (`docker-compose.yml`)
*   Will define the `backend` and `frontend` services.
*   Will map the `frontend` port (e.g., `80`) to a host machine port (e.g., `8080`) for public access: `ports: - "8080:80"`.
*   Will use volumes for local development, allowing code reloading without rebuilding images.
*   Will define volumes to persist log files generated by both services.

## 7. Non-Functional Requirements

### 7.1. Testing
*   **Unit Tests (Backend):** Must cover all business logic functions, especially:
    *   The level conversion function, with test cases for `"FF"`, `"99"`, `"50"`, and `"0"`.
    *   The `Hold` time calculation function.
    *   The parsing functions for the different sections of the Picolo file.
*   **API/Integration Tests (Backend):** Test the `/api/v1/convert` endpoint with a valid file and verify that the output XML is correct. Test with invalid files to ensure appropriate error responses.

### 7.2. Logging
*   Both `frontend` and `backend` services must generate logs.
*   Logs should record success events (request received, conversion completed) and error events (invalid file, internal error).
*   **Important:** User-uploaded files and generated files should not be saved. Logging is for telemetry and debugging only.

### 7.3. Modularity
The strict separation between the frontend and backend is a key requirement to allow the conversion engine to be reused in the future by other applications (e.g., a native desktop application).
